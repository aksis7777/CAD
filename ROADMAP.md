# Дорожная карта

Нормативные требования и решения: [PDM_RULES.md](PDM_RULES.md). Состояние реализации: [PROJECT_STATE.md](PROJECT_STATE.md). Этапы задают последовательность работ и не меняют правил.

## Этап 1 — каркас, Storage и ядро импорта

1. Создать solution и проекты API, Desktop, Contracts, Domain, Storage, функциональные модули и тестовый проект; настроить DI через расширения модулей. **Каркас, Avalonia Desktop shell и регистрация серверных модулей созданы.**
2. Создать доменную модель объектов, версий, состояний, текущей версии, состава и массы. **Доменная модель, проверки атрибутов/состава и правила переходов реализованы и используются импортом и ручными командами.**
3. Описать EF Core маппинг, ограничения уникальности и количества, конкурентные токены. Создать и проверить миграции PostgreSQL. **`InitialCreate`, `AddImportJournalAndStandardName` и `AddBackgroundTasks` сохранены в репозитории; все три миграции применены на временной PostgreSQL 17.**
4. Реализовать Storage с общим scoped `PdmDbContext`, узкими контрактами команд и сохранением атомарных операций. Создать CTE-запрос дерева в Storage; интерфейс и экран чтения реализовать на этапе 2. **Атомарная запись импорта, его журнал, изменение графа и query дерева на одном recursive CTE реализованы; mapping не требует миграции.**
5. Реализовать файловые upload/source, JSON Adapter для `.a3d`/`.m3d`, Iterator и `ICadSourceFactory`. **Реализовано для отдельных JSON-файлов, не ZIP.**
6. Реализовать проверку полного пакета: валидация, дубли, объединение одинаковых компонентов с предупреждением, отсутствующие/отклонённые ссылки, циклы и каскадное отклонение. **Реализовано; пакет частично принимается с отчётом по каждому файлу.**
7. Реализовать правила повторного импорта, Saga файлов + БД, `import-id` для идемпотентности, отмену до сохранения и восстановление незавершённого импорта. **Повторный импорт, журнал/idempotency и файловая Saga реализованы; `ImportSourceRecovery` подключён к startup и расписанию фоновой задачи, HTTP smoke подтвердил очистку только orphan-папок и сохранение успешных исходников.**
8. Реализовать блокировку изменений графа advisory lock, optimistic concurrency и защиту текущей версии. **Импорт и четыре ручные команды используют общую PostgreSQL advisory lock; ручные команды сравнивают клиентский expected token после блокировки и проверяют будущий действующий граф до атомарной записи.**
9. Проверить сценарии тестами: ошибки пакета и каскад, циклы, дубли, повторный импорт, конкурентное изменение, rollback/compensation и идемпотентность. **Финальная проверка: build 0 warnings/0 errors; 123 solution tests (79 Modules, 33 Storage, 11 Desktop) и 11 PostgreSQL tests прошли без пропусков — 134 всего.**

Критерии этапа: solution собирается; миграции из репозитория разворачивают схему на PostgreSQL 17; пакет сохраняет допустимые документы согласованно; повторный импорт применяет правила версий; отчёт содержит ошибки/предупреждения. **Сборка, все 134 теста и import/version HTTP smoke прошли на временной БД.**

## Этап 2 — чтение и расчёты

1. Реализовать поиск и карточку через DTO-проекции. **Готово: `GET /api/objects` с буквальным case-insensitive поиском и `HasMore` offset-пагинацией; `GET /api/objects/{id}` с выбором текущей или исторической версии. Реализация — no-tracking projection, без чтения файлов. Автотесты и HTTP-проверки на временной PostgreSQL 17 прошли.**
2. Реализовать API-запрос дерева состава поверх рекурсивного CTE, созданного в Storage на этапе 1. **Готово: `ICompositionReadQuery`, один PostgreSQL recursive CTE и endpoint состава с путями вхождений.**
3. Реализовать расчёт массы и плоскую сводную спецификацию с количеством по всем путям. **Готово: endpoint расчётов использует один результат CTE и чистую доменную логику.**
4. Обрабатывать отсутствующую массу/текущую версию как определено в PDM_RULES. **Готово: null-масса листа сохраняет известное количество; переполнение количества делает его неизвестным; любая диагностика даёт null итоговую массу и `IsComplete = false`, при сохранении известных строк спецификации.**

Критерии: запрос дерева — один CTE; расчёты учитывают вложенность и сообщают точный проблемный компонент. **Tree/calculation, Objects read endpoints, версии и direct historical BOM проверены по HTTP на временной PostgreSQL 17. Финальная проверка включает 134 теста без пропусков.** PostgreSQL suite в отдельном `tests/MiniPdm.Postgres.Tests` вне solution использует выделенную БД через `PDM_TEST_POSTGRES_CONNECTION`: read-query тесты откатывают транзакции, concurrent-write тесты создают случайные fixtures и удаляют только собственные записи. Standard solution suite остаётся SQLite/pure.

## Этап 3 — версии и администрирование

1. Реализовать создание версии из выбранной, редактирование атрибутов и состава. **Реализованы и проверены clone, attribute update и полная замена BOM через API/handlers, общий доменный planner и атомарную Storage-команду.**
2. Реализовать разрешённые переходы состояний и обновление `current_version_id`. **Реализовано с fallback на максимальную неаннулированную версию после отмены и проверкой будущего графа; HTTP smoke проверил успешный fallback и блокировку циклического fallback.**
3. Сохранить ограничения редактирования утверждённых/аннулированных версий. **Проверено: утверждённая/аннулированная версия не редактируется, запрещённый обратный переход даёт 409. Финальные build и 134 теста прошли.**

## Этап 4 — API и Desktop UI

1. Реализовать Controllers/Contracts и MediatR handlers модулей. **Backend endpoints и handlers чтения, импорта, расчёта и мутаций версий присутствуют и проверены build/tests/HTTP smoke.**
2. Реализовать Avalonia MVVM: поиск, карточка, дерево, импорт/отчёт, расчёт и спецификация. **Shell и модульные UI реализованы; headless preview и VM проверки прошли, включая блокировку Approved, редактируемость InWork и корректную доступность количеств. Native display server в среде не использовался.**
3. Проверить пользовательские сценарии через HTTP. **Проверены поиск/карточка, CAD import, расчёты, version clone/state/attributes/composition, графовые конфликты и concurrency; фоновые HTTP сценарии приведены на этапе 5.**

## Этап 5 — фоновые задачи и завершение

1. Подключить `ImportSourceRecovery` к запуску и периодическому выполнению API. **HTTP smoke на временной PostgreSQL подтвердил три миграции, startup cleanup, manual 202/Succeeded, 1 accepted + 11 conflicts под graph lock, persistent interval через API restart, повтор с интервалом в одну минуту и сохранность успешных исходников.**
2. Реализовать страницу задач с расписанием, состоянием, последним результатом, ошибкой и ручным запуском. **Страница и команды реализованы и входят в headless preview/VM verification.**
3. Прогнать оба приложенных набора CAD, проверить версии между `cad-export` и `cad-export-v2`. **Оба полных набора по 45 файлов проверены через API; импорт `cad-export-v2` после утверждения текущих версий создал две новые версии, 33 принятых документа не изменились. Import retry учтён в Desktop VM тестах.**
4. Подготовить README с запуском, выбранными технологиями и обоснованием отличий от рекомендованной схемы ТЗ. **README содержит запуск API/Desktop, миграции, ограничение source download и однокомандный Docker Compose quick start.**
5. Подготовить локальное контейнерное окружение для API, базы, миграций и Desktop. **Dockerfile имеет цели API, migration bundle и Desktop; Compose управляет PostgreSQL health, миграцией, API и noVNC Desktop. Добавлены браузерная стартовая страница и same-origin `/import/` для выбора локальной папки с Mac и отправки пакета существующему endpoint; показаны итоговые статусы, диагностики и безопасный повтор с тем же ID. Реальная проверка браузера с Chromium и временной PostgreSQL подтвердила `/import/`, redirect `/import`, 35 принятых, 10 отклонённых, одно предупреждение и 45 строк отчёта, duplicate basename guard и retry с тем же payload/ID. Полную сборку Docker images ещё предстоит проверить.**

Критерии завершения: требования обязательной части ТЗ реализованы; сборка и тесты проходят; схема воспроизводится миграциями; UI/API и отчётность доступны; README описывает запуск и подтверждённые отклонения.
