# Мини-PDM: единые правила проекта

Дата фиксации: 30.09.2026.

## 1. Назначение и статус правил

Это единый документ с требованиями задания, решениями из обсуждения и оставшимися вопросами. При дальнейшем обсуждении обновлять этот файл, не создавать параллельные документы с другими правилами.

Источник требований: «Тестовое задание .NET - Мини-PDM.pdf» и набор cad-export.zip. Файл «Тест.doc» / test.doc исключён из рассмотрения по указанию пользователя.

Статусы:

- **ТЗ** — обязательное требование исходного задания.
- **Согласовано** — решение или дополнение пользователя.
- **Предложено** — рекомендуемая реализация, ещё не утверждённая отдельно.
- **Уточнить** — решение пока не принято; не выдавать его за согласованное.

Последние явные решения пользователя имеют приоритет. Расхождения с исходным заданием должны быть явно описаны в README. Не считать вопрос пользователя утверждением конкретной реализации.

## 2. Объём и технологии

**ТЗ:** настольное приложение для импорта CAD-документов, хранения объектов и их версий в реляционной БД, расчёта состава изделия и работы через интерфейс.

| Область | Требование / допустимый выбор | Решение проекта |
| --- | --- | --- |
| Платформа | .NET 8 или новее | Уточнить версию |
| Интерфейс | WPF или Avalonia, MVVM | Уточнить |
| СУБД | Реляционная БД с рекурсивными CTE | Уточнить |
| Доступ к данным | Dapper, EF Core или ADO.NET | Уточнить |
| Композиция | DI-контейнер либо ручная композиция | Единая точка сборки зависимостей |
| Тесты | xUnit, NUnit или MSTest | Уточнить |

Стек работодателя — Dapper, Jab, xUnit, PostgreSQL / MS SQL — даёт дополнительный плюс, но не является обязательным выбором.

## 3. Объекты и идентичность

**ТЗ:** существуют три типа объектов.

| Тип | Идентификатор объекта PDM | Масса | Материал |
| --- | --- | --- | --- |
| Assembly — сборка | Обозначение | Вычисляется по составу | Не задаётся |
| Part — деталь | Обозначение | Масса одной штуки | Обязателен |
| StandardPart — стандартное изделие | Наименование | Масса одной штуки | Не задаётся |

Обозначение — четыре заглавные кириллические буквы, точка, шесть цифр, точка, три цифры. Пример: АБВГ.301245.001. Латинские буквы, визуально похожие на кириллические, не подходят.

Обозначение уникально совместно среди сборок и деталей. Наименование уникально среди стандартных изделий. Одинаковые наименования разных деталей или сборок сами по себе не означают дубликат.

Не смешивать идентификаторы: имя файла идентифицирует входной CAD-документ, обозначение / наименование идентифицирует объект PDM, внутренний ID идентифицирует запись БД.

**Согласовано:** изменение обозначения даже у того же файла означает новый объект. Старому объекту не заменять обозначение и не переносить его историю автоматически. Ссылки новой импортируемой модели разрешаются заново по документам пакета.

**Предложено:** изменение идентифицирующего наименования стандартного изделия означает новый объект; отдельный устойчивый идентификатор для распознавания переименования отсутствует.

## 4. Защита от дубликатов

**Согласовано:** нужна простая проверка, защищающая оператора от случайного создания одинаковых объектов. Векторная БД и семантический поиск в этот механизм не включаются.

**Предложено:** для стандартных изделий формировать единый ключ сравнения названия: убрать пробелы по краям, свернуть повторяющиеся пробелы и единообразно обработать регистр. Сохранять исходное отображаемое название. Не удалять размеры, марки, номера ГОСТ и другие значимые символы.

Проверка перед сохранением и ограничения уникальности в БД должны использовать одинаковые правила сравнения. Для деталей и сборок проверять обозначение, для стандартных изделий — ключ наименования.

**ТЗ:** при повторном импорте существующий идентификатор означает обработку существующего объекта по правилам версий, а не создание дубликата объекта.

**ТЗ:** если в одном пакете у нескольких файлов одинаковое обозначение, отклонить все эти файлы. Не выбирать первый и не превращать конфликтующие документы в последовательные версии.

Повторный импорт стандартного изделия с изменившейся массой также подчиняется правилам версий. Это отдельный сценарий от двух конфликтующих файлов одного пакета.

**Уточнить:** обработку двух файлов стандартных изделий с одинаковым ключом наименования в одном пакете, особенно при разных массах. Наличие версий само по себе не определяет, какой из этих файлов считать новой редакцией.

**Предложено:** при похожих, но не совпадающих названиях стандартных изделий показывать предупреждение оператору. Не объединять объекты автоматически. Например, «Болт М8×25» и «Болт М8×30» — разные изделия.

## 5. Версии и состояния

**ТЗ:** номер версии — положительное целое число, уникальное внутри объекта. Состояния: «В работе», «Утверждено», «Аннулировано».

Разрешённые переходы:

| Из состояния | В состояние |
| --- | --- |
| В работе | Утверждено |
| В работе | Аннулировано |
| Утверждено | Аннулировано |

Обратных переходов нет. Утверждённые и аннулированные версии не редактируются. Аннулированные версии не участвуют в расчётах.

**ТЗ:** текущая версия — версия с наибольшим номером среди неаннулированных. При создании и аннулировании версии поддерживать current_version_id.

**Согласовано:** выбирать историческую версию для просмотра можно. Активировать аннулированную версию обратным переходом нельзя. Для восстановления её данных использовать отдельную команду оператора «Создать новую версию на основе выбранной»: копировать атрибуты и состав в новую версию «В работе».

**Согласовано:** аннулирование не создаёт новую версию. Решение о ручном создании новой версии принимает оператор отдельной командой. Это не отменяет автоматическое создание версии при повторном импорте изменённого утверждённого объекта, которое требует ТЗ.

Важно: после аннулирования самой новой версии текущей может стать предыдущая неаннулированная версия. Это обновление указателя, а не создание версии и не ручная активация аннулированной версии.

Правила повторного импорта:

| Ситуация | Действие |
| --- | --- |
| Данные действующей версии не изменились | Ничего не менять |
| Данные изменились, текущая версия «В работе» | Обновить текущую версию |
| Данные изменились, текущая версия «Утверждено» | Создать следующую версию «В работе» |
| Все версии аннулированы | Создать следующую версию «В работе», сохранив историю |

Последняя строка — согласованное дополнение к ТЗ. Новый номер определяется по всем версиям объекта: максимальный номер плюс один.

**Предложено:** сравнивать содержательные атрибуты и состав; изменение порядка строк компонентов, пробелов JSON или порядка его полей не считать изменением объекта.

**Предложено:** наименование деталей и сборок хранить в версии вместе с материалом и массой, чтобы изменение названия не переписывало историю утверждённых версий. Идентифицирующее наименование стандартного изделия учитывать отдельно как ключ объекта. Изменение рекомендованной схемы объяснить в README.

## 6. Состав изделия

**ТЗ:** связь состава соединяет версию сборки-родителя с дочерним объектом, а не с конкретной версией дочернего объекта. В расчётах использовать текущую версию дочернего объекта.

Количество — целое число строго больше нуля. Пара «версия родителя + дочерний объект» уникальна в БД.

Один объект может встречаться в разных ветках и на разных уровнях дерева. Такое повторение допустимо и само по себе не является циклом. Цикл возникает при повторении объекта на одном пути обхода.

Утверждение сборки фиксирует её собственные атрибуты и связи, но не фиксирует версии её компонентов. Поэтому масса утверждённой сборки может измениться при изменении текущей версии дочернего объекта — это следствие модели ТЗ.

**Согласовано:** повторяющиеся строки одного компонента внутри одной сборки выводить оператору в UI для решения. Не записывать несколько одинаковых связей в БД.

**Уточнить:** конкретные действия оператора при повторяющихся строках — объединение количеств, исправление количества или отклонение сборки. UI передаёт решение сервису; итоговая валидация выполняется в бизнес-логике.

**Уточнить:** поведение, если аннулирование текущей версии возвращает предыдущий состав и создаёт цикл в действующем графе. Этот случай не связан с созданием новой версии.

## 7. Импорт

**ТЗ:** импортируются документы папки. Файлы .a3d — сборки, .m3d — детали и стандартные изделия. Содержимое — JSON UTF-8, независимо от расширения. Ссылки компонентов задаются именами файлов той же папки.

Работа с источником документов и чтение содержимого выполняются через интерфейсы CAD-адаптера. Бизнес-логика импорта не использует Directory, File, JSON-парсер и знания о конкретной САПР.

Ошибки входных данных обрабатывать следующим образом:

- Повреждённый или невалидный документ не импортировать; остальные документы продолжать обрабатывать.
- Файлы с одинаковым обозначением отклонять все.
- Количество компонента не больше нуля — отклонить всю сборку.
- Ссылка на отсутствующий или отклонённый документ — отклонить сборку. Распространять отклонение на все зависящие от неё сборки вверх по графу.
- Обнаруживать циклы. **Предложено:** отклонять участвующие в цикле сборки и распространять отклонение на их родителей.
- Деталь без массы принять с предупреждением. Не подменять отсутствующую массу нулём.

Импорт папки сохраняется в транзакции. Невалидные документы исключаются из плана сохранения; корректные сохраняются согласованно. **Предложено:** при неожиданной ошибке сохранения откатывать транзакцию и показывать причину.

Отчёт содержит файл, результат и причину, а также количества принятых и отклонённых объектов и объектов с предупреждениями. Принятый с предупреждением объект входит в число принятых.

Существование старой записи в БД не должно скрывать ошибку входного компонента текущего пакета и отменять каскадное отклонение, предусмотренное ТЗ.

## 8. Масса и сводная спецификация

**ТЗ:** хранится масса в килограммах за одну штуку, а не вес как сила. Тип хранения массы — decimal. Для сборки масса вычисляется, не вводится вручную.

Расчёт учитывает все уровни вложенности: количества перемножаются вдоль пути, результаты разных путей складываются.

Сводная спецификация — плоский список деталей и стандартных изделий с суммарным количеством и массой. Повторные вхождения одного объекта объединяются по его идентификатору, а не только по отображаемому названию.

Если у детали нет массы, расчёт сборки сообщает, у какого компонента отсутствует масса, и не возвращает ноль или неполную сумму. В спецификации для такого компонента показывается пустая масса.

**Предложено:** отсутствие действующей версии компонента также считать препятствием для полного расчёта и сообщать о нём оператору.

**Уточнить:** допустимость нулевой массы и отдельное правило для отрицательной массы. Уточнение термина «масса» само по себе не задаёт границы допустимых значений.

## 9. Исходные файлы и фоновая очистка

**Согласовано:** сохранять в БД ссылку на исходный CAD-файл. При обращении к отсутствующему файлу выдавать исключение, которое UI преобразует в понятное сообщение.

**Согласовано:** предусмотреть фоновую задачу очистки, выполняющуюся вне UI-потока.

Не смешивать ссылку на исходник и хранилище PDM: по ТЗ атрибуты, версии и связи состава сохраняются в реляционной БД. Путь к файлу дополняет эти данные. Дерево выбирается из БД, а не восстанавливается чтением исходных файлов при каждом расчёте.

**Уточнить:** что именно очищается — недействующие ссылки, журнал, временные файлы или объекты PDM; как часто; что происходит с историей и зависимыми сборками. Исчезновение исходника пока не зафиксировано как команда удаления объекта или его версий.

**Уточнить:** влияет ли отсутствие исходного файла на просмотр уже импортированной карточки и расчёты из БД или ошибка возникает только при открытии / повторном чтении исходника. Не выдавать один вариант за утверждённый.

## 10. Архитектура и паттерны

**Согласовано:** обязательные принципы проектирования — SOLID, DRY и KISS. Основной способ построения приложения — композиция компонентов и контракты через интерфейсы (протоколы).

### 10.1. Принципы проектирования

- **SOLID / SRP:** компонент отвечает за одну связную область. Чтение CAD, сохранение PDM, правила версий, расчёты и UI имеют отдельные ответственности.
- **SOLID / OCP:** новый CAD-адаптер или способ хранения подключается через согласованные интерфейсы; бизнес-логика не переписывается под конкретную реализацию.
- **SOLID / LSP:** реализации одного интерфейса взаимозаменяемы и соблюдают его контракт, включая результаты, ошибки и отмену.
- **SOLID / ISP:** интерфейсы небольшие и соответствуют нуждам потребителя. Не объединять все операции приложения в один универсальный интерфейс.
- **SOLID / DIP:** бизнес-логика зависит от интерфейсов. Конкретные зависимости выбираются в точке композиции и передаются через конструкторы.
- **DRY:** каждое бизнес-правило имеет единое место реализации. UI, импорт и ручное редактирование используют общие проверки и правила версий. Общую логику переиспользовать через композицию.
- **KISS:** выбирать простое решение, достаточное для согласованных требований. Каждый дополнительный слой, интерфейс и паттерн должен решать конкретную задачу; не создавать универсальные механизмы на случай гипотетического расширения.

### 10.2. Композиция и интерфейсы

**Согласовано:** контракты описывать интерфейсами; поведение собирать из переданных компонентов. Не вводить собственные абстрактные базовые классы и иерархии наследования для переиспользования бизнес-логики, CAD-адаптеров, репозиториев и итераторов.

Общую реализацию выносить в отдельный компонент и подключать через композицию. Обязательное наследование, навязанное выбранным фреймворком, отдельно обсуждать до реализации.

Ранее предложенные абстрактные классы итератора и агрегата отменены. Сохраняются роли источника документов и итератора, реализованные через интерфейсы и композицию.

### 10.3. Обязательное обсуждение паттернов

**Согласовано:** использование паттернов проектирования обязательно. Выбор каждого паттерна и изменение его применения всегда обсуждать с пользователем до написания соответствующего кода.

При обсуждении указать:

1. Какую конкретную задачу решает паттерн.
2. Какие интерфейсы и компоненты участвуют и как они связываются через композицию.
3. Почему выбранная схема соответствует SOLID, DRY и KISS.
4. Какие дополнительные сложности она вводит.

После согласования фиксировать решение в этом файле. Не внедрять, заменять или удалять паттерн молча. Уже обсуждённые роли Factory, Repository и Iterator уточнять на уровне конкретных контрактов перед реализацией. Обязательность паттернов не задаёт их количество и не требует отдельного паттерна для каждой функции.

### 10.4. Роли компонентов

| Компонент | Ответственность |
| --- | --- |
| CAD-репозиторий / источник | Предоставляет документы или их идентификаторы, скрывает получение списка из источника |
| ICadDocumentReader | Читает один документ и возвращает модель, независимую от JSON |
| CAD-адаптер | Содержит файловые операции и разбор JSON; позже заменяется адаптером API САПР |
| Factory | Создаёт / выбирает подходящий адаптер источника |
| Контракт источника документов | Предоставляет итератор для обхода документов |
| Контракт итератора | Задаёт последовательный обход без зависимости потребителя от устройства источника |
| PDM-репозиторий | Работает с объектами, версиями и связями в реляционной БД |
| Сервисы приложения | Координируют импорт, версии, состояния, расчёты и проверки прав |
| ViewModel | Управляет состоянием экрана и вызывает сервисы |

Таблица описывает ответственности, а не обязательный отдельный класс для каждой строки. Конкретные контракты и границы компонентов обсуждаются перед реализацией.

**Предложено:** для асинхронного обхода использовать IAsyncEnumerable<T> / IAsyncEnumerator<T> с поддержкой CancellationToken. Если нужны дополнительные контракты, оформлять их интерфейсами; общую логику подключать через композицию.

**ТЗ:** зависимости собираются в одной точке, передаются через конструкторы. Сервисы не создают самостоятельно конкретные SQL- и файловые зависимости.

**ТЗ:** дерево состава из БД получать одним рекурсивным CTE. Итератор CAD-документов не заменяет это требование; не выполнять отдельный SQL-запрос для каждого узла.

## 11. UI и права

**ТЗ:** MVVM, без бизнес-логики в code-behind. Экран предоставляет дерево состава, карточку выбранного объекта, поиск по обозначению / названию, смену состояния, импорт с отчётом, расчёт массы и сводную спецификацию.

**Согласовано:** разрешить ручное редактирование атрибутов и состава только роли «Администратор». Ограничение проверяется в сервисе приложения, а не только скрытием кнопок.

У администратора сохраняются ограничения жизненного цикла: напрямую редактировать можно версию «В работе». Для изменения утверждённой версии необходимо создать новую. Права администратора не разрешают обратные переходы состояний.

Редактирование состава относится к сборкам; массу сборки вычислять. Изменение обозначения создаёт новый объект согласно согласованному правилу.

**Уточнить:** способ определения роли и права на импорт, смену состояния и команду создания версии. Ручное редактирование администратором согласовано; полноценная система учётных записей отдельно не утверждена.

## 12. Проверки и сдача

**ТЗ:** автоматические тесты покрывают расчёт массы, сводную спецификацию, циклы, обозначения, переходы состояний и граничные случаи. Импорт тестируется с подменой ICadDocumentReader без обращения к файловой системе. Источник документов также должен допускать подмену, если выделен отдельно.

Дополнительные сценарии проверки согласованных правил: смена обозначения создаёт новый объект; восстановление создаёт следующую версию; аннулирование само по себе версию не создаёт; повторный импорт не создаёт дубликат объекта; администратор не изменяет утверждённую версию напрямую.

Схема создаётся скриптом или миграцией из репозитория. Решение собирается командой dotnet build и тестируется командой dotnet test; ручная настройка допускается только для строки подключения.

README должен объяснять запуск, СУБД и схему, архитектуру, принятые решения и отклонения от рекомендованной модели, незавершённые части и отчёты по двум наборам данных.

Для проверки версий сначала импортировать cad-export, утвердить необходимые объекты и затем импортировать cad-export-v2. Во втором наборе изменены масса «Колесо зубчатое.m3d» с 5.86 до 5.92 кг и количество прокладок в «Крышка подшипника в сборе.a3d» с 3 до 4. Остальные неизменившиеся документы не должны получать новые версии только из-за повторного импорта.

По исходному ТЗ срок — не более семи календарных дней; результат — Git-репозиторий либо архив с папкой .git и README. Адрес сдачи указан в PDF. Автоматическая отправка результата не запрошена.

## 15. Правила работы моделей

**Согласовано:** правила этого раздела обязательны для разработки проекта.

Цель — минимизировать расход токенов без заметной потери качества разработки.

### Распределение ролей

**Astra**

Использовать только для:

- сложных архитектурных решений;
- выбора подхода между несколькими вариантами;
- анализа сложных проблем;
- проектирования крупных изменений.

Astra не пишет основной код. Результат её работы — решение и подробные инструкции для реализации.

**Sol**

Использовать для:

- задач средней сложности;
- декомпозиции задач;
- анализа существующего кода;
- подготовки технических инструкций для Luna;
- обязательного ревью кода после реализации Luna.

Sol может исправлять план или инструкции, но основной код пишет Luna.

**Luna**

Использовать для:

- написания кода;
- тестов;
- рефакторинга по готовому плану;
- документации;
- простых исправлений;
- рутинных задач.

Luna не должна самостоятельно принимать существенные архитектурные решения. Если в процессе реализации возникает архитектурный вопрос, задача передаётся Sol или Astra.

### Рабочий процесс

Простая задача:

`Luna → код`

Средняя задача:

`Sol → план/инструкции → Luna → код → Sol → ревью`

Сложная или архитектурная задача:

`Astra → архитектурное решение → Sol → технический план → Luna → код → Sol → ревью`

При обнаружении серьёзной архитектурной проблемы на ревью:

`Sol → Astra → обновлённое решение → Luna`

### Документация проекта

Проект должен содержать документацию, достаточную для продолжения разработки другой нейросетью без необходимости заново исследовать весь код.

Поддерживать в актуальном состоянии:

- `AGENTS.md` — обязательные правила работы моделей;
- `ARCHITECTURE.md` — архитектура и основные решения;
- `PROJECT_STATE.md` — текущее состояние проекта;
- `ROADMAP.md` — следующие задачи;
- документацию публичных API и сложной логики непосредственно в коде.

Перед изменением существующей архитектуры модель обязана ознакомиться с этой документацией.

### Главное правило

Не использовать более дорогую модель, если задача надёжно решается более дешёвой.

При этом качество важнее экономии: если Luna не может уверенно выполнить задачу по имеющимся инструкциям, она не должна угадывать — задача эскалируется Sol, а архитектурная проблема — Astra.
