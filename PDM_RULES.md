Дата фиксации: 01.10.2026.

## 2. Объём и технологии

**ТЗ:** настольное приложение для импорта CAD-документов, хранения объектов и их версий в реляционной БД, расчёта состава изделия и работы через интерфейс.

| Область | Решение проекта |
| --- | --- |
| Платформа | .NET 10 LTS |
| UI | Avalonia, MVVM |
| API | ASP.NET Core Controllers |
| Команды и запросы | CQRS через MediatR |
| СУБД | PostgreSQL |
| Доступ к данным | EF Core; проект `MiniPdm.Storage` |
| DI | Стандартный контейнер ASP.NET Core, единая точка композиции |
| Тесты | xUnit |

Решения соответствуют допустимым технологиям исходного ТЗ. Рекомендованный стек задания (Dapper, Jab, xUnit, PostgreSQL / MS SQL) не обязателен; выбран EF Core. Приложение состоит из Avalonia-клиента и ASP.NET Core API. HTTP-контракты размещаются в `MiniPdm.Contracts`.

Локальный запуск предоставляется через Dockerfile и Docker Compose одной командой `docker compose up -d --build`; PostgreSQL и применение EF Core миграций запускаются автоматически. Согласованный дополнительный режим запускает Docker API/PostgreSQL и native Avalonia окно; noVNC Compose режим сохраняется. Native launcher использует Compose project `cad` по умолчанию, публикует API только на loopback и не останавливает backend при закрытии окна.

В Docker Compose noVNC сразу показывает единственное окно Avalonia. Импорт и его отчёт остаются в Avalonia через одну кнопку выбора папки. При запуске в контейнере стандартный файловый диалог Avalonia видит только файловую систему контейнера, поэтому кнопка использует расширение выбора файлов: браузер noVNC показывает краткий диалог выбора папки на компьютере, а выбранные `.a3d`/`.m3d` файлы передаются Avalonia через локальный bridge и далее по обычному API импорта. Отдельной страницы или интерфейса импорта в браузере нет. Из-за браузерной защиты открытие системного выбора требует явного нажатия в небольшом диалоге поверх окна noVNC после запроса из Avalonia. Диалог включает подходящие файлы во вложенных каталогах; адаптер проверяет лимиты API и одинаковые basenames, поскольку ссылки в CAD-пакете основаны на имени файла. При неизвестном исходе API-запроса Avalonia удерживает выбранные файлы и тот же `importId`; начать отдельную операцию можно только после явного подтверждения пользователя.

## 3. Объекты и идентичность

**ТЗ:** существуют три типа объектов.

| Тип | Идентификатор объекта PDM | Масса | Материал |
| --- | --- | --- | --- |
| Assembly — сборка | Обозначение | Вычисляется по составу | Не задаётся |
| Part — деталь | Обозначение | Масса одной штуки | Обязателен |
| StandardPart — стандартное изделие | Наименование | Масса одной штуки | Не задаётся |

Обозначение — четыре заглавные кириллические буквы, точка, шесть цифр, точка, три цифры. Пример: АБВГ.301245.001. Латинские буквы, визуально похожие на кириллические, не подходят.

Обозначение уникально совместно среди сборок и деталей. Наименование уникально среди стандартных изделий. Одинаковые наименования разных деталей или сборок сами по себе не означают дубликат.

Не смешивать идентификаторы: имя файла идентифицирует входной CAD-документ, обозначение / наименование идентифицирует объект PDM, внутренний ID идентифицирует запись БД.

**Согласовано:** изменение обозначения даже у того же файла означает новый объект. Старому объекту не заменять обозначение и не переносить его историю автоматически. Ссылки новой импортируемой модели разрешаются заново по документам пакета.

**Согласовано:** изменение идентифицирующего наименования стандартного изделия означает новый объект; отдельный устойчивый идентификатор для распознавания переименования отсутствует.

## 4. Защита от дубликатов

**Согласовано:** нужна простая проверка, защищающая оператора от случайного создания одинаковых объектов. Векторная БД и семантический поиск в этот механизм не включаются.

**Согласовано:** для сравнения наименований стандартных изделий обрезать пробелы по краям, сворачивать последовательности пробелов и сравнивать без учёта регистра; исходное наименование сохранять для отображения. Размеры, марки, номера ГОСТ и знаки не удалять. В частности, `×` и латинскую `x` автоматически не приравнивать.

**Предложено:** показывать предупреждение для похожих, но не совпадающих нормализованных наименований. Такие объекты не объединять автоматически.

Предварительная проверка и ограничение уникальности в БД используют одинаковый ключ. Обозначение уникально совместно среди сборок и деталей; нормализованное наименование уникально среди стандартных изделий.

**ТЗ:** при повторном импорте существующий идентификатор означает обработку существующего объекта по правилам версий, а не создание дубликата объекта. Если в пакете несколько файлов имеют одинаковое обозначение, отклонить все такие файлы.

**Согласовано:** если в одном пакете несколько файлов стандартных изделий имеют одинаковый нормализованный ключ имени, отклонить все конфликтующие файлы; не выбирать источник автоматически. Повторный импорт одного такого изделия из отдельного пакета подчиняется правилам версий.

Изменение обозначения даже у того же файла означает новый объект. Изменение идентифицирующего имени стандартного изделия также означает новый объект: устойчивого отдельного идентификатора для распознавания переименования нет.

## 5. Версии и состояния

**ТЗ:** номер версии — положительное целое число, уникальное внутри объекта. Состояния: «В работе», «Утверждено», «Аннулировано».

Разрешённые переходы:

| Из состояния | В состояние |
| --- | --- |
| В работе | Утверждено |
| В работе | Аннулировано |
| Утверждено | Аннулировано |

Обратных переходов нет. Утверждённые и аннулированные версии не редактируются. Аннулированные версии не участвуют в расчётах.

**ТЗ:** текущая версия — версия с наибольшим номером среди неаннулированных. При создании и аннулировании версии поддерживать `current_version_id`.

**Согласовано:** историческую версию можно просматривать. Активировать аннулированную версию обратным переходом нельзя. Для восстановления её данных отдельной командой оператора создать следующую версию «В работе», копируя атрибуты и состав.

Аннулирование не создаёт новую версию. После аннулирования самой новой версии текущей может стать предыдущая неаннулированная версия. Это обновление указателя, а не создание версии.

Правила повторного импорта:

| Ситуация | Действие |
| --- | --- |
| Содержательные данные действующей версии не изменились | Ничего не менять |
| Данные изменились, текущая версия «В работе» | Обновить текущую версию |
| Данные изменились, текущая версия «Утверждено» | Создать следующую версию «В работе» |
| Все версии аннулированы | Создать следующую версию «В работе», сохранив историю |

Последняя строка — согласованное дополнение к ТЗ. Новый номер — максимум по всем версиям объекта плюс один. Автоматическое создание новой версии при повторном импорте изменённого утверждённого объекта сохраняется по ТЗ.

**Согласовано:** сравнивать содержательные атрибуты и состав. Для детали/сборки сравнивать наименование, материал, массу и нормализованный состав; для стандартного изделия — нормализованное идентифицирующее имя и массу. Путь к исходному файлу не влияет на создание версии. Изменение порядка строк состава после объединения повторов, форматирования JSON или порядка полей JSON не создаёт новую версию.

Наименование и остальные изменяемые атрибуты деталей и сборок хранить в версии, чтобы история утверждённых версий не переписывалась. Идентифицирующее наименование стандартного изделия хранится на объекте. Это отклонение рекомендованной схемы ТЗ; обосновать его в README.

## 6. Состав изделия

**ТЗ:** связь состава соединяет версию сборки-родителя с дочерним объектом, а не с конкретной версией дочернего объекта. В расчётах использовать текущую неаннулированную версию дочернего объекта.

Количество — целое число строго больше нуля. Пара «версия родителя + дочерний объект» уникальна в БД. Один объект может встречаться в разных ветках дерева; цикл — повторение объекта на одном пути.

**Согласовано:** повторяющиеся строки одного компонента в одной сборке объединять сложением количеств и показывать оператору предупреждение. До объединения валидировать каждое входное количество как положительное целое; переполнение суммы отклоняет сборку. В БД сохраняется одна связь на дочерний объект.

Утверждение сборки фиксирует её собственные атрибуты и связи, но не версии её компонентов. Поэтому масса утверждённой сборки может измениться при изменении текущей версии дочернего объекта — следствие модели ТЗ.

**Согласовано:** перед изменением состава или текущей версии проверять будущий действующий граф. Операцию, которая создаёт цикл, блокировать с диагностикой пути цикла. Это включает аннулирование, если после обновления `current_version_id` активный граф стал бы циклическим.

## 7. Импорт

**ТЗ:** импортируются документы папки. Файлы `.a3d` — сборки, `.m3d` — детали и стандартные изделия. Содержимое — JSON UTF-8 независимо от расширения. Идентификатор CAD-документа — имя файла; ссылки компонентов задаются именами файлов той же папки.

Avalonia отправляет выбранные CAD-файлы в ASP.NET Core API. Сервер принимает пакет, временно хранит его и выполняет проверку и импорт. Постоянные исходники хранятся в отдельной серверной папке. Ссылка на исходник привязана к версии. S3 и API САПР — возможные будущие источники; сейчас их не реализовывать.

Работа с источником и чтение CAD-документа изолированы интерфейсами. `.a3d` и `.m3d` — один JSON-формат, поэтому текущая файловая реализация читает оба расширения. Реализации для отличающихся форматов или API создаются отдельными адаптерами. `ICadSourceFactory` используется уже сейчас и выбирает адаптер по описанию/типу источника.

Ошибки обрабатывать так:

- Повреждённый или невалидный документ не импортировать; обработку остальных документов продолжать.
- Если файлы одного пакета имеют одинаковое обозначение, отклонять все конфликтующие документы.
- Если файлы стандартных изделий имеют одинаковый нормализованный ключ имени, отклонять их все.
- Неположительное количество компонента или переполнение объединённой суммы — отклонить сборку.
- Ссылка на отсутствующий или отклонённый документ — отклонить сборку. Распространять отклонение вверх на все зависящие от неё сборки.
- Обнаруживать циклы пакета; отклонять участвующие в цикле сборки и распространять отклонение на их родителей.
- Деталь без массы принять с предупреждением. Не подменять отсутствующую массу нулём.
- Отрицательную массу отклонять; нулевую принимать с предупреждением.

Сначала подготовить и проверить план всего пакета. Допустимые документы записать в одной транзакции БД; невалидные исключить из плана, чтобы сохранить требование частичного импорта.

Импорт согласует файловые операции и транзакцию БД как локальная Saga: загрузка во временное хранилище → проверка → перенос исходников допустимых документов в постоянную область импорта → атомарная запись данных и записи импорта в БД. При подтверждённом rollback выполнить компенсацию (удалить перенесённые файлы). Если процесс завершился или результат commit неизвестен, восстановление сначала сверяет запись импорта в БД; используемые исходники не удалять. Незавершённые временные и осиротевшие файлы обрабатывает фоновая очистка.

Отмена разрешена до начала сохранения. После начала сохранения операция завершается commit/rollback и возвращает итог. `import-id` служит ключом идемпотентности: повтор запроса с тем же ID не запускает повторную запись и возвращает результат / состояние исходного импорта.

Отчёт содержит файл, результат, причину, количества принятых и отклонённых документов и документов с предупреждениями. Принятый с предупреждением объект входит в число принятых.

Существование старой записи в БД не должно скрывать ошибку входного компонента текущего пакета и отменять каскадное отклонение, предусмотренное ТЗ.

## 8. Масса и сводная спецификация

**ТЗ:** хранится масса в килограммах за одну штуку, не сила тяжести. Тип — `decimal`. Масса сборки вычисляется по составу, вручную не вводится.

**Согласовано:** PostgreSQL `numeric(18,6)` и `decimal` в приложении. Значения, которые нельзя сохранить с указанной точностью без округления, диагностировать; молча не округлять. Отрицательная масса невалидна; нулевая допустима с предупреждением. Для детали с отсутствующей массой сохранять отсутствие значения и предупреждение.

Расчёт учитывает вложенность: количества перемножаются вдоль пути, результаты разных путей складываются. Сводная спецификация — плоский список деталей и стандартных изделий, объединённый по идентификатору объекта. При отсутствующей массе расчёт не возвращает ноль или неполную сумму, а сообщает компонент; в спецификации масса такой строки пуста.

**Согласовано:** при отсутствии текущей неаннулированной версии компонента показывать компонент с ошибкой в дереве; полный расчёт массы блокировать с объяснением. Не подставлять ноль и не выбирать аннулированную версию.

## 9. Исходные файлы и фоновые задачи

**Согласовано:** импортированные исходные CAD-файлы сохранять на сервере в папке импорта, не перезаписывая файлы успешных импортов. В БД хранить ссылку на исходник версии. Отсутствие исходного файла сообщает об ошибке только при попытке открыть или перечитать его; карточка, дерево и расчёты из БД продолжают работать.

Фоновая очистка выполняется вне UI-потока внутри API: при старте сервера и затем раз в сутки. Она удаляет временные загрузки, а также файлы незавершённых/неудачных импортов после сверки с БД. Историю PDM и исходники успешных импортов автоматически не удалять.

**Согласовано:** отдельный модуль и страница «Фоновые задачи». Страница показывает задачу, расписание, состояние, время и результат последнего запуска, ошибку; администратор может изменить расписание и запустить задачу вручную. Фоновые задачи исполняются внутри API-процесса.

Расписание и последнее состояние/результат задачи хранятся в PostgreSQL. Интервал задаётся в минутах, начальное значение — 1440. Исполнитель реализуется как прямой `IHostedService`, без `BackgroundService`; запуск при старте, плановый и ручной запуск сериализуются в одном API-процессе, параллельные запуски одной задачи не допускаются. Подключение модулей API выполняется через callback композиции приложения. Распределённый планировщик и cron в текущий объём не входят.

## 10. Архитектура и паттерны

**Согласовано:** принципы проектирования — SOLID, DRY, KISS; модульное приложение; FSA внутри модулей; CQRS через MediatR. Команды изменяют состояние, запросы читают данные. Отдельные БД и Event Sourcing не вводить. Все модули работают с одной PostgreSQL БД.

### 10.1. Модульность и структура

Серверные функциональные модули: `Import`, `Objects`, `Versions`, `Composition`, `Calculations`, `BackgroundTasks`. Каждый модуль при необходимости содержит папки `Controllers`, `Features`, `DtoModels`, `Services`, `Abstractions`, `Infrastructure`, `Extensions` на одном уровне. Внутри `Features` команды и запросы размещаются раздельно (`Commands/<Scenario>` и `Queries/<Scenario>`). Если у сценария есть MediatR message и handler, их публичные типы находятся вместе в одном `Command.cs` или `Query.cs` внутри папки сценария; validators остаются отдельными файлами. Публичные HTTP DTO размещаются один раз в `MiniPdm.Contracts/Modules/<Module>/DtoModels`; модули и клиент ссылаются на них, не дублируя модели. Типы, размещённые в любой папке `DtoModels` (как в Contracts, так и во внутренних модулях), являются DTO, имеют суффикс `Dto` и объявляются как `sealed record` без positional-параметров в заголовке. Каждый член DTO задаётся явным свойством `public T Name { get; init; }`, снабжённым собственным содержательным XML-summary. DTO создаются object initializer-ами. Перечисления остаются перечислениями; суффикс `Dto` для них не обязателен. Это соглашение не меняет форму доменных типов, MediatR-запросов и команд, сервисных проекций или конфигураций вне `DtoModels`.

При переводе существующих DTO на это соглашение сохранять исходные имена свойств, значения по умолчанию и JSON-контракты. Переносить проверки DataAnnotations с параметров positional-конструктора на соответствующие свойства, сохраняя их атрибуты и ограничения. Явные свойства инициализировать так, чтобы десериализация сохраняла прежнее поведение при отсутствующем поле, JSON `null` или default-значении; не вводить новые требования обязательности и не менять контракты ошибок.

Основные проекты: `MiniPdm.Api`, `MiniPdm.Desktop`, `MiniPdm.Contracts`, `MiniPdm.Domain`, `MiniPdm.Storage`; отдельные проекты `MiniPdm.Modules.<Module>`; тестовые проекты. Контроллеры принадлежат своим модулям и подключаются серверным хостом через расширения регистрации. Desktop зависит от Contracts и вызывает API по HTTP. API подключает модули и Storage. Domain не зависит от UI, API, Storage или EF Core. Серверные модули используют Domain, Contracts и Storage: их scoped-сервисы могут получать общий scoped `PdmDbContext` напрямую для сборки EF Core-запросов и сохранения. `MiniPdm.Storage` предоставляет контекст, entity mappings, миграции, регистрацию EF Core и общие инфраструктурные механизмы конкурентности/графа. Обязательная прослойка репозиториев или persistence-интерфейсов между сервисами модулей и контекстом не вводится. Узкие внутренние интерфейсы допустимы как локальная граница модуля или тестовый seam, когда для этого есть конкретная причина; не дублировать ими API DbContext. Все зависимости собираются в точке композиции и передаются через конструкторы.

`MiniPdm.Storage` содержит `PdmDbContext`, `Configurations`, `Migrations` и EF Core registration. Общий механизм PostgreSQL advisory lock и повторно используемые инфраструктурные DB helpers могут оставаться в Storage; конкретные запросы и сценарии данных принадлежат сервисам соответствующих модулей. Миграции создаются сравнением модели с ModelSnapshot (`dotnet ef migrations add`), проверяются и применяются (`dotnet ef database update`). Маппинг Fluent API не является миграцией. PostgreSQL schema/namespace пока не выбиралась; не предполагать имя `pdm`.

### 10.2. Потоки CQRS и доступа к данным

HTTP Controller (все endpoints данного модуля собраны в его Controllers) → MediatR `ISender` → command/query handler → сервис этого функционального модуля → при необходимости `PdmDbContext`/общий инфраструктурный механизм. Handler маршрутизирует сценарий и вызывает сервис; сервис содержит прикладную оркестрацию и строит нужную работу с данными. MediatR не заменяет доменные правила и сам по себе не требует HTTP API для каждого сообщения.

Команды и запросы размещаются в отдельных папках `Features/Commands` и `Features/Queries`. EF-запрос ленив: построение `IQueryable` само по себе не обращается к БД; материализация (`ToListAsync`, `SingleAsync` и т.п.) отправляет SELECT немедленно. Для DTO использовать `Select` и выбирать только нужные поля; для entity-чтения применять `AsNoTracking`. `Include` использовать, когда сценарию действительно нужны связанные entity. Не загружать весь граф без необходимости. Дерево состава — обязательное исключение: один рекурсивный CTE, отображаемый в модель чтения через EF Core; не выполнять N+1 запросы и не заменять CTE цепочкой `Include`. Для записи отслеживаемые изменения отправляются вызовом `SaveChangesAsync`; один вызов может породить несколько SQL-команд. Для согласованного многошагового сценария явно сохранять необходимые транзакционные границы и блокировки.

Один scoped `PdmDbContext` обеспечивает отслеживание в рамках операции и выполняет роль Unit of Work; сервисы одного запроса получают его через DI. Собственный Unit of Work не вводить. Для saga recovery/неизвестного commit, фонового singleton-координатора и других случаев, которым нужны отдельные границы/свежий snapshot, использовать `IDbContextFactory<PdmDbContext>` или scope с новым контекстом; не хранить DbContext в singleton. Не вводить обязательные универсальные или модульные репозитории между модульным сервисом и DbContext. Узкие сервисные интерфейсы оставлять лишь как обоснованную локальную границу или тестовый seam.

### 10.3. Конкуренция графа и транзакции

Оптимистический токен конкурентности хранится на объекте и обновляется при любом изменении атрибутов версии, состава или `current_version_id`; конфликт отклоняется, данные перечитываются, автоматической слепой перезаписи нет. Номер версии PDM — бизнес-номер версии, не concurrency token. Уникальные ограничения БД защищают обозначения/ключи и номер версии.

Изменения состава и текущей версии сериализуются одной транзакционной PostgreSQL advisory lock. После получения блокировки операция читает актуальный действующий граф, проверяет будущий граф на циклы и сохраняет его до освобождения блокировки на commit/rollback. Это дополняет оптимистические токены и защищает от параллельных изменений разных объектов, которые вместе создали бы цикл.

### 10.4. Обязательное обсуждение и выбранные паттерны

**Согласовано:** паттерны проектирования обязательны там, где они решают конкретную задачу; выбор каждого паттерна и изменение способа его применения обсуждать до написания соответствующего кода. Указывать задачу, компоненты/интерфейсы, композицию, соответствие SOLID/DRY/KISS и добавленную сложность. Решение фиксировать здесь. Это не требует паттерна для каждой функции. Не вводить паттерн без конкретной задачи. Обязательное наследование, навязанное фреймворком, также обсуждать до реализации.

- **Adapter:** скрывает конкретный источник и формат CAD за интерфейсом. Сейчас файловый JSON адаптер читает `.a3d` и `.m3d`; при появлении другого формата/API у него отдельная реализация. Бизнес-логика не зависит от JSON/файлов. Цена — интерфейсы и преобразование ошибок/моделей.
- **Factory:** создаёт/выбирает CAD-адаптер по типу источника; используется сразу, файловый источник — первая реализация, позднее можно подключить S3/API без изменения импорта. Это решение выбора реализации, DI лишь предоставляет зарегистрированные адаптеры. Цена — фабрика и описание источника; не создавать универсальную фабрику для объектов приложения.
- **Iterator:** источник документов предоставляет асинхронный последовательный обход (`IAsyncEnumerable<T>` с отменой); отдельная собственная иерархия итераторов не нужна. Цена — правила отмены и освобождения ресурса источника.
- **Repository:** обязательный repository-layer между сервисом модуля и EF Core не используется: модульный сервис строит запрос через scoped `PdmDbContext`. Узкая внутренняя абстракция допустима лишь при явной потребности тестирования или отдельной инфраструктурной границе. Цена обязательного репозитория — контракты и риск дублировать API `DbContext`.
- **CQRS / Mediator:** сообщения и MediatR отделяют транспортный вход от сценариев; контроллеры отправляют команды/запросы, handlers оркестрируют. Цена — косвенный переход и больше небольших типов; отдельная БД и Event Sourcing не вводить.
- **MVVM:** отделяет состояние/команды UI от представления и API-вызовов; code-behind без бизнес-логики. Цена — ViewModels и уведомления состояния.
- **Saga для импорта:** компенсирует файловые действия при сбое вокруг транзакции БД; используется локальная Saga без брокера. Цена — журнал/идемпотентность, восстановление незавершённых операций и осторожная компенсация при неизвестном commit.

Strategy отдельным паттерном не вводить, пока нет самостоятельных взаимозаменяемых алгоритмов. State-классы не нужны: правила переходов централизованы в домене. Template Method не применять для переиспользования бизнес-логики; общий поток строится композицией компонентов. Не вводить собственные базовые классы ради переиспользования.

### 10.5. Принципы

- **SRP/OCP/ISP/DIP/LSP:** модули имеют согласованные ответственности; зависимости направлены к контрактам, реализации выбираются в точке композиции и соблюдают интерфейсы.
- **DRY:** одинаковые доменные проверки общие для импорта и ручных операций.
- **KISS:** слои и паттерны существуют только при решаемой задаче; без универсальных абстракций «на будущее».

## 14. Ресурсы сообщений и типизированные исключения

**Согласовано:** тексты ошибок и валидационных сообщений хранить в `.resx` ресурсах общей библиотеки `MiniPdm.Common`. Для `BusinessLogicException` и `InputLogicException` использовать конструкторы, принимающие готовый текст сообщения. Вызов передаёт значение ресурса напрямую, например `throw new BusinessLogicException(Resources.BusinessLogicException.Error_Model_Object);`; не передавать отдельный код/ключ, не искать текст по имени ошибки через `nameof` и не добавлять параметры форматирования в конструкторы исключений. Аргументы `string.Format` допустимы только там, где существующая диагностика требует динамических значений.

`MiniPdm.Common` не зависит от других проектов решения. Серверные модули и Contracts ссылаются на него по необходимости. API централизованно обрабатывает только эти два типа новых исключений и преобразует их в HTTP 400/409 с `ProblemDetails`; существующие коды результатов доменных мутаций, диагностики циклического пути, предупреждения и статусы фоновых/импортных операций сохраняются. Не заменять структурированные доменные результаты общей ошибкой исключения. Для DataAnnotations использовать `ErrorMessageResourceType` и `ErrorMessageResourceName`, указывающие на соответствующую пару ресурсов.

Значения ресурсов сохраняют текущие английские тексты ошибок и валидации; отдельный выбор языка интерфейса в эту работу не входит.

## 16. Правила работы моделей

**Согласовано:** правила этого раздела обязательны для разработки проекта.

Цель — минимизировать расход токенов без заметной потери качества разработки.

### Распределение ролей

**Astra**

Использовать только для:

- сложных архитектурных решений;
- выбора подхода между несколькими вариантами;
- анализа сложных проблем;
- проектирования крупных изменений.

Astra не пишет основной код. Результат её работы — решение и подробные инструкции для реализации.

**Sol**

Использовать для:

- задач средней сложности;
- декомпозиции задач;
- анализа существующего кода;
- подготовки технических инструкций для Luna;
- обязательного ревью кода после реализации Luna.

Sol может исправлять план или инструкции, но основной код пишет Luna.

**Luna**

Использовать для:

- написания кода;
- тестов;
- рефакторинга по готовому плану;
- документации;
- простых исправлений;
- рутинных задач.

Luna не должна самостоятельно принимать существенные архитектурные решения. Если в процессе реализации возникает архитектурный вопрос, задача передаётся Sol или Astra.

### Рабочий процесс

Простая задача:

`Luna → код`

Средняя задача:

`Sol → план/инструкции → Luna → код → Sol → ревью`

Сложная или архитектурная задача:

`Astra → архитектурное решение → Sol → технический план → Luna → код → Sol → ревью`

При обнаружении серьёзной архитектурной проблемы на ревью:

`Sol → Astra → обновлённое решение → Luna`

### Документация проекта

Проект должен содержать документацию, достаточную для продолжения разработки другой нейросетью без необходимости заново исследовать весь код.

Поддерживать в актуальном состоянии:

- `AGENTS.md` — обязательные правила работы моделей;
- `ARCHITECTURE.md` — архитектура и основные решения;
- `PROJECT_STATE.md` — текущее состояние проекта;
- `ROADMAP.md` — следующие задачи;
- документацию публичных API и сложной логики непосредственно в коде.

Перед изменением существующей архитектуры модель обязана ознакомиться с этой документацией.

Для C# использовать форматирование Microsoft/Roslyn: отступы в четыре пробела, пробелы после запятых и между операторами, открывающие фигурные скобки на новых строках. Форматирование задаётся в `.editorconfig` и может применяться/проверяться командами `dotnet format whitespace MiniPdm.sln --no-restore` и `dotnet format whitespace MiniPdm.sln --no-restore --verify-no-changes`.

Для публичных типов и членов писать XML-документацию с многострочным `<summary>`. Каждое объявленное свойство должно иметь собственный содержательный `<summary>` непосредственно над свойством, включая свойства DTO и свойства с непубличным доступом. У параметров методов, конструкторов и объявлений делегатов указывать смысл отдельными тегами `<param>`; для positional types, которые не являются DTO, описание параметра в заголовке не заменяет документацию синтезируемого свойства. Для методов, возвращающих значение, добавлять содержательный `<returns>`; пустые XML-теги не использовать. Не требовать XML-комментарии для всего кода: документировать публичный контракт и логику, смысл которой не очевиден из кода.

### Главное правило

Не использовать более дорогую модель, если задача надёжно решается более дешёвой.

При этом качество важнее экономии: если Luna не может уверенно выполнить задачу по имеющимся инструкциям, она не должна угадывать — задача эскалируется Sol, а архитектурная проблема — Astra.
