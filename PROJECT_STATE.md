# Состояние проекта

Нормативный источник: [PDM_RULES.md](PDM_RULES.md). План следующих шагов — в [ROADMAP.md](ROADMAP.md).

## Сейчас

- Создан solution с API, Avalonia Desktop, Contracts, Domain, Storage, шестью проектами модулей и тестовыми проектами; PostgreSQL-интеграционный проект расположен отдельно от solution.
- Добавлен запускаемый API с `GET /health`, подключением контроллеров модулей и MediatR. Desktop содержит Avalonia shell, HTTP-клиент, основные экраны объектов/версий/состава/импорта и страницу фоновых задач.
- Domain содержит правила версии и состояния, проверки атрибутов и состава, а также общий поиск циклов действующего графа. Эти правила используются импортом и ручными командами изменения версий.
- Storage содержит EF Core/Npgsql mapping, ключи/ограничения, composite FK текущей версии, scoped `PdmDbContext`, `IDbContextFactory<PdmDbContext>`, токен конкурентности и проверку точности массы. Миграции `InitialCreate`, `AddImportJournalAndStandardName` и `AddBackgroundTasks` остались в Storage. После рефакторинга все три миграции применены на свежей временной PostgreSQL 17; `has-pending-model-changes` подтвердил, что новая миграция не требуется. Постоянная пользовательская база не настраивалась.
- Доступ к данным переведён из обязательных Storage repositories/contracts в scoped services функциональных модулей. `Objects.Services.ObjectReadService`, `Composition.Services.CompositionReadService`/`VersionCompositionReadService`, `Calculations.Services.CompositionCalculationService` и `Versions.Services.VersionMutationService` используют injected `PdmDbContext`; общий graph lock/запрос графа остаётся в `MiniPdm.Storage/Concurrency`. Import оставляет локальный `IImportDatabaseService`/`ImportDatabaseService` seam для saga и неизвестного результата commit, а BackgroundTasks — scoped `IBackgroundTaskDatabaseService`/`BackgroundTaskDatabaseService` под singleton coordinator. В каждом модуле CQRS-команды и запросы лежат в `Features/Commands` и `Features/Queries`; сообщение и handler размещены вместе в `Command.cs`/`Query.cs` соответствующего сценария, handlers вызывают сервисы.
- Импорт реализован от HTTP до module services: загрузка отдельных CAD JSON-файлов, Factory/Iterator/JSON reader, проверка документов и графа, частичное принятие пакета, создание версий, отчёт, повторный импорт, журнал идемпотентности, сериализация изменения графа и согласование файлов с транзакцией. `ImportSourceRecovery` возвращает диагностики, восстанавливает/очищает источники и пропускает активные upload leases; API вызывает его при запуске и планирует повторы через фоновую задачу с persistent расписанием.
- Проверены оба полных набора `cad-export` и `cad-export-v2` по 45 файлов. В `cad-export` принято 35, отклонено 10, одно предупреждение о пустой массе. После утверждения текущих версий импорт `cad-export-v2` создал версии для двух объектов и оставил 33 принятых документа без изменений. Повторная отправка того же `import-id` возвращает прежний отчёт; конкурентные запросы с одним ID не дублируют запись.
- Повторный импорт в Desktop: исправлен `DataContext` содержимого вкладки отчёта — контекст привязан к корневому `Grid`, а не к `TabItem`, чей контекст может заменить Avalonia `TabControl`. Новые headless UI-тесты проверяют контекст/строки, два импорта подряд с фактическим `IsEnabled`, `_isPicking`, `IsBusy` и `PendingImportId`, отмену выбора и повтор после HTTP 503 с тем же ID.
- Текущая проверка: `dotnet test MiniPdm.sln --no-restore` — 133 теста без пропусков (79 Modules, 33 Storage, 21 Desktop). Docker Desktop image пересобран и контейнер Desktop пересоздан; API/DB остались healthy, named volumes `cad_postgres-data` и `cad_source-files` сохранены. В noVNC-браузере после пересборки виден отчёт прежнего импорта (45 строк); отмена папочного picker вернула HTTP 204. Второй успешный браузерный импорт не подтверждён из-за блокировки macOS при открытом системном диалоге.
- Текущая проверка после переноса EF-сценариев в module services: `dotnet build MiniPdm.sln` завершился с 0 warnings и 0 errors; прошли 130 solution tests и 11 PostgreSQL tests — всего 141. EF Core применил все три существующие миграции к свежей PostgreSQL 17 и подтвердил отсутствие ожидающих изменений модели.
- Чтение дерева выполняется `Composition.Services.CompositionReadService` через один PostgreSQL recursive CTE; `Calculations.Services.CompositionCalculationService` использует этот сервис для endpoint массы/спецификации. Плоские вхождения сохраняют повторные появления с разными путями. Расчёт выполняется чистой доменной логикой по одному результату CTE; неизвестная масса листа сохраняет известное количество, но даёт null для его масс. Переполнение количества даёт null quantity. Любая диагностика приводит к `TotalMassKg = null` и `IsComplete = false`, известные строки спецификации остаются. Интеграционные PostgreSQL-тесты в `tests/MiniPdm.Postgres.Tests` требуют `PDM_TEST_POSTGRES_CONNECTION`: тесты чтения откатывают транзакции, concurrent-write тесты очищают только созданные ими случайные fixtures; таблицы не очищаются и чужие данные не затрагиваются.
- Реализованы и проверены по HTTP поиск и карточка объектов через `GET /api/objects` и `GET /api/objects/{id}`. Поиск — буквальный регистронезависимый поиск по обозначению, имени текущей действующей версии и имени StandardPart; `%`, `_` и `\\` экранируются. Пагинация принимает `offset >= 0`, `limit 1..100`, `search <= 512`, определяет `HasMore` дополнительной строкой и не делает `COUNT`. Карточка по умолчанию выбирает current version, по `?version=N` может показывать любую историческую версию, включая Cancelled. Нет текущей версии — `200` с null selected version и `NoCurrentVersion`; отсутствующий объект или запрошенная версия — `404`, пустой GUID и неположительная версия — `400`. DTO карточки содержит идентичность, current pointer и concurrency token; выбранная версия полная с `SourceReference`, история — только metadata. Для Assembly масса в карточке null и берётся из calculation endpoint. Запросы используют no-tracking projections, без полной загрузки сущностей или чтения файлов.
- Реальная HTTP-проверка Objects на временной PostgreSQL 17 подтвердила 35 уникальных результатов в пяти страницах по 7, case-insensitive поиск кириллицей по колесам и стандартным болтам, буквальный поиск `%`, статус-коды для неверной пагинации/поиска/версии и пустого GUID. Все 35 текущих карточек имели верные token/current pointer; имя StandardPart совпало в header/selected version; масса Assembly null. Тестовый fixture также подтвердил read-only чтение объекта без current version и Cancelled historical version.
- HTTP-команды клонирования версии, изменения состояния, атрибутов и состава вызывают `VersionMutationService` с общей advisory lock, проверкой expected token после блокировки, проверкой будущего графа и атомарной записью. HTTP smoke после рефакторинга прошёл: импорт принял 35 файлов, отклонил 10 и выдал одно предупреждение; повторный импорт оставил 33 документа без изменений и создал две версии. Проверены конкурентное клонирование (201/409), атрибуты, BOM, циклы и отмена версии.
- HTTP smoke-проверка на временной PostgreSQL подтвердила `cad-export` (35 принято, 10 отклонено, 1 предупреждение), начальную массу `РДЦЛ.304112.000` 98.804 кг и импорт `cad-export-v2` (2 `NewVersion`, 33 `Unchanged` после утверждения 35 текущих версий). Проверены clone, token и immutability conflicts, атрибуты/валидация, BOM merge/removal, self-cycle и циклический fallback, cancelled-only object с null current и восстановлением clone, а также конкурентный clone (201/409). Скрипт — `/tmp/pdm-versions-http-smoke.py`.
- До переноса EF работы в module services HTTP smoke на временной PostgreSQL проверил подробные сценарии startup recovery, блокировки параллельного запуска и сохранения расписания после рестарта. Этот прежний smoke не считается проверкой этих сценариев для текущего кода.
- После переноса фоновой работы в module service HTTP проверка на временной PostgreSQL подтвердила список задач, изменение расписания и ручной запуск `202` с итогом `Succeeded`.
- Avalonia UI прошёл headless capture и проверки доступности/биндингов: актуальный InWork editor доступен, Approved editor заблокирован, количество для состава доступно. VM тесты покрывают stale selection, 409 с сохранением введённого значения и повтор импорта. Нативный GUI запуск с реальным display server не выполнялся.
- Добавлена Docker Compose схема с PostgreSQL 17, одноразовым EF Core migration bundle, ASP.NET Core API и Avalonia Desktop через noVNC. Корневой URL сразу показывает единственное окно Avalonia; отдельной browser import page нет, API не раздаёт static files и не публикует host port. Вызов кнопки импорта в контейнерном Avalonia Desktop открывает небольшой noVNC overlay: пользователь явным нажатием запускает browser directory picker и передаёт CAD файлы во встроенный picker bridge. Фильтрация `.a3d`/`.m3d`, лимиты и проверка одинаковых basenames выполняются в расширении; API upload, отчёт и безопасный повтор остаются в текущем Avalonia import flow. Папку Mac не требуется копировать в контейнер. Из-за browser user activation нужен один клик в overlay после нажатия кнопки в Avalonia. DB/source files хранятся в named volumes. Порт Desktop опубликован только на `127.0.0.1`. В Desktop-образе задана UTF-8 locale и установлен DejaVu для кириллицы. Ранее Chromium проверил JS расширение через реальный Kestrel bridge, ImportViewModel, API и временную PostgreSQL: 35 принятых, 10 отклонённых, одно предупреждение, 45 строк отчёта; staging-файлы удалены. Picker прекращает polling и отменяет текущий pending-запрос на `pagehide`, запускает ровно один цикл на `pageshow`, ограничивает ожидание pending HTTP-ответа и его JSON body 10 секундами, переносит overlay внутрь fullscreen элемента noVNC и сбрасывает busy state после завершения или ошибки отмены/загрузки, чтобы принимать следующий запрос. Изолированные Chromium проверки `tests/browser/pdm-picker-lifecycle.test.cjs` покрывают эти lifecycle случаи, stale JSON, stalled HTTP headers/body, fullscreen overlay и cancel/retry/upload; локальный HTTP fixture раздаёт picker CSS. Полный GUI noVNC в Docker и пользовательский Mac не проверялись.

## Следующая работа

Следующая проверка — собрать и запустить все Compose образы целиком, затем проверить стартовую страницу и Avalonia через noVNC на пользовательском Mac. Нативный Avalonia GUI вне контейнера также ещё не запускался с реальным display server. Локальный Compose запуск поставляет собственную PostgreSQL и автоматически применяет миграции; для отдельного развёртывания API нужна своя строка подключения. Возможные будущие расширения остаются в [PDM_RULES.md](PDM_RULES.md); авторизация, загрузка исходных CAD-файлов обратно из PDM и интеграции CAD не входят в завершённую текущую реализацию. Имя PostgreSQL-схемы ещё не утверждено; `public` используется как техническая настройка PostgreSQL по умолчанию.
